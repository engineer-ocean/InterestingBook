0导读：这篇论文要解决什么

一句话概括：LLM 服务的核心瓶颈不是"算力不够"，而是显存被 KV Cache 管得太浪费。论文把操作系统的虚拟内存 + 分页思想搬进 GPU，提出 PagedAttention，并以此为基础造出工业级推理引擎 vLLM。

论文的三根支柱，构成了本讲义的主线：

01
算法层：PagedAttention

把 KV Cache 切成固定大小的块，允许非连续存储，消除碎片并实现块级共享 → 吞吐提升 2–4×。

02
系统层：vLLM 引擎

统一调度抽象、分层架构、可插拔后端，既跑得快又能快速适配新模型与新硬件。

03
生态层：开源社区

模型厂商、硬件厂商、云厂商与研究者共同维护，成为事实标准（影响 TensorRT-LLM、SGLang 等）。

核心论点

高效的 LLM 推理本质上是一个系统问题，而不是单纯的模型结构问题或硬件加速问题。真正卡住吞吐的是内存管理——碎片化 + 无法共享。

1第一讲 背景：LLM 推理为什么这么难对应 Ch.1–2

本讲目标：理解"自回归生成"如何导致 GPU 利用率低下，KV Cache 为何既是救命稻草又是新的负担，以及真实业务对延迟的硬约束。

1.1 自回归生成的两副面孔：Prefill 与 Decode

LLM 一次前向只能吐出一个新 token，且新 token 依赖前面所有 token——这就是自回归。它把一次推理切成两个性格截然不同的阶段：

直观感受：一个 8B 参数模型，BF16 权重 16 GB。以 3.35 TB/s 带宽，光是把权重读一遍就要 5 ms——与 GPU 算得快不快无关。要让 decode 转成算力受限，需要把几百个请求凑成一个批次，而这又受限于显存（KV Cache）和延迟要求。§2.1.1

1.3 KV Cache：把 O(L²) 降到 O(L)，却带来新麻烦

注意力机制要求每个新 token 都要"回看"之前所有 token 的 Key / Value：

Attention(Q, K, V) = softmax( Q Kᵀ / √d_k ) · V

如果每一步都重算全部历史 K/V，生成 L 个 token 的代价是 O(L²)。于是有了 KV Cache：把历史 K/V 存下来，每步只算新 token 的 K/V，代价降为 O(L)。

长序列下 attention 访存成为新瓶颈

KV Cache 带来的三大麻烦：

  • 显存占用：随序列长度与批次线性增长，往往主导 GPU 显存，直接限制并发请求数。
  • 访存压力：decode 时每步都要读整个 KV Cache。
  • 碎片化：请求长度不一且动态变化。按最大长度预分配 → 内部碎片；动态分配 → 外部碎片。这正是第 3 章要解决的核心问题
贯穿全文的根本矛盾

大批次 → 算术强度高、GPU 利用率高、吞吐高，但需要更多 KV Cache 显存；小批次 → 延迟低但 GPU 饿着。
所以：KV Cache 管得越好 → 能塞进内存的请求越多 → 吞吐越高。

1.4 MoE：省了算力，没省显存

混合专家（MoE）让每个 token 只走少量专家。例如 256 个专家、top-8 路由：单 token 计算量相对同规模稠密模型降低约 32×，但所有专家权重仍要全部驻留显存。

更麻烦的是批次要求被放大：批次中 b 个 token 按路由分散到 E 个专家、每 token 走 k 个，则每个专家平均只拿到 b·k/E 个 token。256 专家 + top-8 → 每个专家的有效批次缩小 32 倍。要达到和稠密模型同样的算术强度，MoE 需要 32 倍大的批次。§2.2

1.6 六大趋势：问题只会越来越严重

📈 模型更大

千亿/万亿参数仍是竞争力选项，显存、算力、通信三线吃紧。

📏 上下文更长

128K 已成常态，百万级出现；RAG、长文档、多轮对话推高 KV Cache 需求。

🖼️ 多模态输入

一张图上千 token，一段视频可达十万级 token，prefill 与 KV Cache 同步放大。

🤖 Agent 工作流

多次串行调用、依赖复杂，端到端延迟关键，请求模式也更难批处理。

🔧 硬件演进失衡

算力增速快于带宽增速，decode 的访存受限只会更明显。

💰 成本压力

大规模部署动辄数千 GPU、兆瓦级功耗，效率直接等于钱。

第一讲小结

  • 自回归把推理切成 prefill（并行、算力受限） 与 decode（串行、访存受限） 两半。
  • 要救 decode，就得加大批次；要加大批次，就得省显存；而显存大头是 KV Cache。
  • KV Cache 又大、又动态、又没法预测长度——传统"连续内存 + 预分配"的管理方式会浪费掉一大半。
  • 于是问题被收敛为一句话：如何把 KV Cache 的显存管到近乎零浪费？

2第二讲 PagedAttention：把虚拟内存搬进 GPU对应 Ch.3

本讲目标：掌握 PagedAttention 的算法原理、块表机制、四种内存共享场景、抢占恢复策略，以及它为什么能带来 2–4× 吞吐提升。

2.1 旧方案的三宗浪费

由于主流深度学习框架（PyTorch 等）要求 tensor 连续存储，早期服务系统（Orca、FasterTransformer）也把一个请求的 KV Cache 存成一整块连续显存，并按最大可能长度预分配。

图 2：显存利用率对比（数据来自原文 Fig. 3.2）

三种浪费分别是：

  • 预留（reserved）：为"将来可能生成的 token"提前占位，整个请求生命周期都占着。
  • 内部碎片（internal fragmentation）：按最大长度（如 2048）分配，实际只用几百 token，剩下的永远用不上。
  • 外部碎片（external fragmentation）：每个请求分配尺寸不同，伙伴分配器（buddy allocator）产生无法利用的空洞。
两个反直觉的事实：
① 即使预知输出长度（论文中的 Orca-Oracle 理想基线），预留机制仍会造成大量浪费。
② 内存紧凑化（compaction）理论上能治碎片，但 KV Cache 动辄几十 GB，在服务系统中做搬运不现实。

2.2 核心洞见：操作系统早就解决过这个问题

KV Cache 有三个独特性质：动态增长、生命周期与长度事先未知、但天然按" token 序列"线性组织。这恰好和 OS 面对的进程内存问题同构。

操作系统虚拟内存vLLM / PagedAttention作用
页（page）KV 块（KV block）固定大小的管理单元
字节（byte）token被管理的最小数据单位
进程（process）请求（request）申请内存的主体
页表（page table）块表（block table）逻辑地址 → 物理地址映射

为什么分页能同时解决三个问题

块小 → 内部碎片被限制在一个块内；块大小统一 → 不存在外部碎片；按需分配 → 不为未来 token 预留整块空间；块可共享 → 多个序列映射同一物理块。

2.3 PagedAttention 算法

把 KV Cache 切成长度为 B（block size）的块，记第 j 个块的 Key/Value 为 K_j = (k_{(j-1)B+1}, …, k_{jB})、V_j。原本逐 token 的注意力，改写成逐块计算：

# 分块注意力（原文式 3.4） A_ij = softmax( q_iᵀ K_j / √d ) # 第 i 个 query 对第 j 个 KV 块的注意力分数 o_i = Σ_{j=1}^{⌈i/B⌉} V_j · A_ijᵀ # 对所有块的输出加权求和

PagedAttention 的 CUDA kernel 会分别定位并抓取各个不连续的 KV 块，再完成上述计算。关键实现点：

  • 一个 GPU warp 负责读取一个块，保证合并访存（coalesced access）；
  • 支持同一批次内变长序列；
  • Token 的 KV 依赖其位置，因此同一 token 在不同位置的 KV 不同——这也是不能简单"内容寻址复用"的原因。
块大小的两难：块太小 → kernel 无法充分利用 GPU 并行度、块表变大；块太大 → 内部碎片增多、共享概率下降。后文消融实验给出答案：默认 16。见 §2.11

2.4 KV Cache Manager：逻辑块、物理块与块表

  • 逻辑块（logical block）：请求视角，从左到右随 token 生成而填满。
  • 物理块（physical block）：GPU 显存中真实的一块固定大小空间，由块引擎统一管理。
  • 块表（block table）：每个请求一张，记录"逻辑块 → 物理块编号 + 已填充槽位数（#filled）"。

2.5 一次完整解码的生命周期（三步走）

① Prefill 阶段：7 个 token 的 prompt → 只分配 2 个物理块（够用即可，不按 2048 预留）。逻辑块 0/1 分别映射到物理块 7/1。前 4 个 token 落块 0，后 3 个落块 1，剩余 1 个槽位留给后续生成。

② 第一个 decode step：用 PagedAttention 在物理块 7、1 上算注意力。最后一个逻辑块还有空位 → 新 KV 直接写入，块表 #filled 更新（3 → 4）。

③ 第二个 decode step：最后一个逻辑块已满 → 分配新的逻辑块与新的物理块（物理块 3），并把映射写进块表。

全局流程（每个 decode 迭代）：调度器挑选候选序列 → 为新逻辑块分配物理块 → 把本轮所有输入 token（prefill 请求的 prompt token + decode 请求的最新 token）拼成一条序列送入模型 → PagedAttention kernel 按块表读取历史 KV、写入新 KV → 请求完成后块被回收。

2.6 内存共享：四种场景，一套机制

这是 PagedAttention 相对"仅仅消除碎片"的第二重红利：块级共享 + 引用计数 + 写时复制。

图 4：并行采样中的块级共享与写时复制（重绘自原文 Fig. 3.8）

① 并行采样（Parallel Sampling）

同一 prompt 采样 n 个候选：prompt 部分的逻辑块映射到同一批物理块，引用计数 = n。生成阶段各自发散，需要写入共享块时触发 块级写时复制：分配新块 → 拷贝旧块 → 原块引用计数减 1 → 写入新块。

② 束搜索（Beam Search）

比并行采样更复杂：候选之间不只共享 prompt，中间块也能动态共享，且共享模式随解码推进不断变化（类似 OS 中反复 fork 产生的进程树）。

  • 被淘汰的候选 → 其逻辑块释放，对应物理块引用计数递减；
  • 引用计数归零的物理块 → 真正回收；
  • 新候选 → 分配新块。
收益：beam search 场景下可节省高达 55% 的 KV Cache 显存。旧系统需要频繁在候选间拷贝 KV Cache，vLLM 只需在"写入旧共享块"时拷贝一个块。§3.6.3

③ 共享前缀（Shared Prefix）

系统提示词 / few-shot 示例被大量请求共用。服务提供方可以预先把这段前缀的 KV Cache 存成物理块（如同 OS 的共享库），新请求只需把逻辑块映射过去（最后一块标记 COW），prefill 只需计算用户真正的任务输入部分。

④ 混合解码（Mixed Decoding）

为什么能"混批"

块表这一层公共映射层把复杂的共享关系藏了起来：模型与 kernel 只看到"每个序列的物理块 ID 列表"，不需要理解序列之间的共享模式。因此采用不同解码策略的请求可以一起批处理，这进一步扩大了批处理机会、提高了整体吞吐。

2.7 显存不够时：抢占、交换与重算

请求流量超过系统容量时必须做取舍。vLLM 的策略要点：

  • FCFS 顺序：先到先服务，保证公平、防止饥饿；需要抢占时，优先抢占最晚到达的请求。
  • 全有或全无（all-or-nothing）驱逐：一个序列的所有块总是一起被访问，因此要么全驱逐、要么全保留；同一请求内的多序列（如 beam 候选）作为序列组（sequence group）成组调度，一起被抢占或恢复。
  • 两种恢复手段：
换出（Swapping）

把被驱逐的块拷到 CPU 内存（CPU 块分配器管理）。抢占后暂停接收新请求，直到被抢占序列完成、块被换回。
代价：小块尺寸下产生大量细碎传输，PCIe 有效带宽打不上去。

重算（Recomputation）

重新调度时直接重算 KV Cache。巧妙之处：已生成的 token 可与原 prompt 拼成新 prompt，一次 prefill 迭代就能重建全部位置的 KV。
代价：与块大小无关，开销恒定。

消融结论：块小 → 重算更划算；块大 → 交换更划算；块大小在 16–64 之间两者端到端表现接近。且重算开销从不超过交换延迟的 20%。§3.7.3

2.8 分布式执行

大模型往往单卡放不下，需要 Megatron-LM 风格的张量并行（SPMD：线性层按块矩阵乘切分，GPU 间通过 all-reduce 同步中间结果；注意力按头切分）。

关键观察：即使模型被切分，每个模型分片处理的仍是同一批输入 token，因此需要相同位置的 KV Cache。于是 vLLM 在集中式调度器里放唯一一个 KV Cache Manager：所有 worker 共享同一套"逻辑块 → 物理块"映射，只是各自只存自己负责的那部分注意力头的 KV。
流程：调度器准备"输入 token ID + 块表"控制消息 → 广播给 worker → worker 按块表读 KV、用 all-reduce 同步 → 回传采样 token。内存管理无需在 worker 间额外同步。§3.4.6

2.9 实现与实验结果

工程实现

  • 8.5K 行 Python + 2K 行 C++/CUDA；FastAPI 前端 + OpenAI 兼容 API；NCCL 做分布式通信。
  • 三个关键 kernel 优化：① 融合 reshape 与块写入（减少 kernel 启动开销）；② 融合块读取与注意力（改造 FasterTransformer kernel，按块表读取）；③ 融合块拷贝（把 COW 产生的零散拷贝批量化，避免大量 cudaMemcpyAsync 小调用）。
  • 解码算法统一抽象为三个操作：fork（派生序列）、append（追加 token）、free（删除序列）——并行采样、beam search、前缀共享全部由它们组合而成。

实验设置

模型：OPT-13B / 66B / 175B、LLaMA-13B；GPU：A100（13B 单卡 / 66B 四卡 / 175B 八卡）。负载：ShareGPT（长输入长输出、方差大）与 Alpaca（短序列）。基线：FasterTransformer、Orca（Max / Pow2 / Oracle 三种预留策略）。核心指标：归一化延迟（端到端延迟 ÷ 输出长度），越低越好。

一个值得注意的反例：在 OPT-175B + Alpaca 的组合下，vLLM 相对 Orca-Oracle 的优势变小。原因是 175B 配置留给 KV Cache 的显存非常充裕，而 Alpaca 序列又很短——此时瓶颈从显存受限变成了算力受限，内存管理再好也提高不了吞吐。

消融项发现结论
Kernel 微基准动态块映射带来额外开销：查块表、额外分支、处理变长序列 → 注意力 kernel 延迟比高度优化的 FasterTransformer 高 20–26%可接受：只影响注意力算子，不影响 Linear 等其他算子，端到端仍大幅领先

第二讲小结

  • 问题：连续预分配导致预留 + 内部碎片 + 外部碎片，实际利用率仅 20–38%。
  • 方法：分页管理（块=页、token=字节、请求=进程）+ 块表映射 + 按需分配。
  • 红利一：近乎零碎片 → 更大批次 → 更高吞吐（2–4×）。
  • 红利二：块级共享 + 引用计数 + COW → 并行采样、beam search、共享前缀统统受益，还能混合批处理。
  • 工程：全有或全无驱逐、成组调度、集中式 KV Cache Manager 支撑分布式。
  • 取舍：注意力 kernel 有 20–26% 额外开销，但换来整体数量级的吞吐提升——典型"用局部小代价换全局大收益"。

3第三讲 vLLM 系统设计：从算法到工业级引擎对应 Ch.4

本讲目标：理解 vLLM 如何用"统一抽象"化解优化技术爆炸式增长带来的复杂性，并掌握它在调度策略与 CPU 开销上的三板斧。这一章是论文中最具工程洞见的部分。
章节立意

光有 PagedAttention 还不够。真实部署要面对：异构负载、五花八门的模型结构、以及"GPU 越来越快 → CPU 成为新瓶颈"的现实。这需要系统级设计，而非单点算法优化。

3.1 四个目标与三条哲学

🎯 易用（Ease of Use）

最少的信息就能跑起来：用户无需理解引擎内部。

🧩 多模型支持

新模型每周都在发布，引擎必须能快速适配而不用重构。

⚡ 推理优化可集成

投机解码、前缀缓存、PD 分离等新技术要能无缝接入。

🚫 零 CPU 开销

新一代 GPU 上一次前向只要几毫秒，任何 CPU 开销都会被放大。

三条设计哲学

  • Be general（通用）：寻找能统一表达不同优化的抽象，而不是给每个优化单独开一条代码路径。新优化 = 映射进现有抽象。
  • Be flexible（灵活）：不过拟合当前负载，接口与模块化为未来的模型、模态、优化留出空间。
  • Be open（开放）：高效推理的版图太大，任何单一组织都做不完，靠开源协作。

3.4 模型编写框架：让"移植新模型"变轻松

开源模型通常先在厂商私有训练框架里开发，再转成 HuggingFace 格式发布。移植过程极易出错：RMSNorm 的 epsilon、归一化时机、激活函数细节的微小差异，都会导致输出不对且难以排查。

只有两条硬性要求

  • 顶层 Model 类实现 forward(input_ids, positions, input_embeds, intermediate_tensors) → 返回 last hidden states；
  • 注意力必须通过 vLLM 的 Attention API 定义（而非 PyTorch 原生注意力），以便挂上 KV Cache 管理的钩子。

其余完全自由：任意 PyTorch 算子、任意自定义 CUDA kernel、任意控制流。

保留原实现 = 保住正确性。因为不必重写模型代码，数值细节、激活函数、归一化变体全部原样保留。已有工作证明：vLLM 的模型 API 甚至能让推理与训练共用同一份模型代码（配合 TorchTitan），实现逐位一致（bitwise equivalence）。

自动融合 vs 手工融合

RMSNorm、残差连接、SiLU 等都是访存受限算子，理想情况下应与相邻算子融合。但手工融合会破坏干净的层抽象（例如跨层融合 pre-LayerNorm 与前一层残差），且训练框架与推理框架的融合策略往往不同。
vLLM 的解法：交给 torch.compile 自动融合；同时把 Attention 封装成对编译器不透明的自定义算子（隐藏注意力元数据等动态部分），让模型其余部分成为一串可分析、可优化的 tensor 算子。

并行策略：对模型代码几乎零侵入

张量并行 TP

ColumnParallelLinear / RowParallelLinear 直接替换 Linear，自动切权重并处理 all-reduce

流水线并行 PP

注入 pre/post hook，在阶段边界收发 IntermediateTensors

专家并行 EP

封装在 FusedMoE 抽象内部，模型作者无感

上下文并行 CP

封装在 Attention 抽象内部，切分序列维度以支持超长上下文

Renderer API

现代模型的输入输出远比"字符串"复杂：chat 模板、工具调用格式、多模态预处理（占位 token 注入）各不相同且互不兼容。Renderer 提供统一入口 render_prompt()，模型开发者可在其中自由实现任意解析逻辑（如 Qwen-VL 的字符串占位、GPT-OSS 的 token 级工具解析）。

3.5 统一调度框架：整章最核心的洞见★ 重点

传统两阶段视角的困境

传统上我们把推理看成 prefill（一次算完整个 prompt）与 decode（每步一个 token）两个阶段。看起来直观，但一旦叠加各种优化就出现大量"灰色地带"：

  • 投机解码：decode 阶段一次前向处理多个 token——这算 prefill 还是 decode？
  • 前缀缓存：一个 prefill 请求只差 1 个 token 就全部命中缓存——只处理这 1 个 token，算 prefill 还是 decode？

硬套两阶段视角的结果是：系统里堆满各自独立的模式代码路径（prefill batch、micro-batch、decode loop、cache hit、speculative verification…），每种组合都要单独维护，优化之间无法自由组合。

核心洞察

复杂性不来自优化技术本身，而来自缺乏统一的"请求进度"表示。
所有行为其实都可以统一表达为：追踪一个请求在它的 token 序列上推进了多远——无论这些 token 来自 prompt、来自缓存、还是来自模型自己生成的。

两个标量，表达一切

图 6：统一调度的两个状态变量
  • num_total_tokens = |prompt tokens| + |output tokens| —— 表示目标（完整序列有多长）。
  • num_computed_tokens = 已被模型处理（KV 已算好并存入）的 token 数 —— 表示进度。恒有 0 ≤ num_computed_tokens ≤ num_total_tokens。
  • 调度转移规则：每步选一个 Δ（正数，不超过剩余量）处理，然后 num_computed_tokens += Δ；若本步生成了 L_generated 个新 token，则 num_total_tokens += L_generated。

一张表统一所有优化

调度行为 / 优化状态更新白话解释
PrefillΔ = L_prompt一次性推进整个 prompt
DecodeΔ = 1每步只推进一个 token
抢占 Preemptionnum_computed ← 0进度清零（总长不变）
Chunked PrefillΔ < L_prompt把 prompt 拆成多步推进
流式 Prefillnum_total += L_new新 token 到达 → 目标变长，差值为可调度量
前缀缓存num_computed ← L_cached命中部分直接算作"已计算"，只算剩余
PD 分离num_computed ← L_prompt
num_total ← L_prompt + 1		相当于"缓存在远端 GPU 上"的前缀缓存；+1 是 prefill worker 已采样的首个 token
投机解码num_total += L_draft − L_rejected + 1
num_computed += Δ − L_rejected		先乐观地加上草稿 token，验证后按被拒数量回退
这个抽象的威力在于"可组合"。例如：chunked prefill + prefix caching = 选 Δ < L_prompt − L_cached 分块处理未缓存部分；PD 分离 + 本地前缀缓存 = decode 端只需接收剩余 L_prompt − L_cached 的 KV；投机解码草稿过长时可以分块验证。不需要为每种组合单独写代码。
作者坦承的局限：① 该框架假设输出是线性序列，难以表达 beam search 这类动态创建/剪枝的分支结构，或树状投机草稿；② 对于不成熟、不支持全部优化的模型或硬件平台，统一抽象反而增加认知负担——不支持分块 prefill 的平台，用传统的两阶段视角反而更清晰。§4.4.5

3.6 调度策略：从 FIFO 到 SRTF 再到两级调度

① FIFO：简单但有硬伤

按到达顺序处理，逐个请求取 Δ = min(Δ_max, 剩余预算 B)，直到预算耗尽。token budget B 是一次前向能处理的总 token 数上限（典型值 8192）——它同时约束了单步延迟与激活峰值显存，是与吞吐做交换的旋钮。

❌ 队头阻塞

10 万 token 的长 prompt 卡在队首，后面 100 token 的短请求只能干等，尾延迟被严重拉高

❌ 无优先级

交互聊天与离线批处理同等对待，无法表达紧急程度

❌ 无缓存感知

能命中前缀缓存的请求不优先，缓存块可能已被淘汰

论文诚实指出：vLLM 曾用"长 prefill 阈值"这类临时启发式打补丁，但它们脆弱、难推理、难维护——治标不治本。这正是需要更原则性框架的原因。

② SRTF：最短剩余 token 优先

维护 W（等待队列，未调度过） 与 R（运行队列，已调度、持有 KV Cache）；每步从两者中挑 Δ 最小的请求。还有一个细节：内层循环会刷新等待队列请求的 num_computed_tokens——因为调度某个请求可能让其他请求的缓存命中结果变化（两个请求共享 prompt 时，一个先跑完，另一个的剩余量骤降甚至归零）。

✓
天然优先 decode

decode 请求剩余量恒为 1，prefill 请求 > 1 → decode 自动优先，符合"生成中不该被打断"的直觉

✓
TTFT 最优

类似 OS 中 SRPT 可证最优，平均首 token 时延最小；且与 chunked prefill 天然契合（剩余少的长 prompt 会被当成"短的"）

✓
提升缓存命中

命中多的请求剩余量少 → 先被调度 → 缓存块在被淘汰前就被用上

但 SRTF 也有两个致命问题：长 prompt 请求可能饥饿（短请求源源不断就永远轮不到）；以及调度开销大（每步都要遍历等待队列做前缀哈希比对）。

③ 两级调度（Two-Level Scheduling）

图 7：两级调度（重绘自原文 Fig. 4.2）
  • 开销有界：昂贵的缓存命中检查与 Δ 计算只在 ≤8 个请求的 staging 队列内进行；大队列只做 FIFO。
  • 防饥饿：FIFO 保证每个请求最终都能进入 staging；批量补货保证"进了 staging 就一定先调度完"——两者结合给出最坏等待时间的上界。
  • 可叠加优先级：为不同优先级维护各自的 waiting 队列，在应用 SRTF 之前先考虑优先级。

3.7 零 CPU 开销三板斧

为什么现在才强调 CPU

现代硬件上主流模型要跑到 >100 token/s，意味着每步 < 10 ms。此时哪怕 1 ms 的 CPU 开销就是 10% 以上的性能损失。而 vLLM 主体是 Python，还要维护大量调度与 KV Cache 记账，且 GPU 比 CPU 进步更快——CPU 开销只会越来越致命。

第一斧：异步调度（Asynchronous Scheduling）

图 8：同步 vs 异步调度（重绘自原文 Fig. 4.3）

为何可行：调度决策通常不依赖模型输出——num_computed_tokens 与 num_total_tokens 仅凭调度决策就能更新。两个需要特殊处理的边界情况：

  • 前缀缓存：异步下，第 N 步生成的 token D 要等到 N+2 才被登记进缓存，因此刚到的请求 [A,B,C,D] 只能命中 [A,B,C]。实践中这种情况罕见，收益远大于损失。
  • 投机解码：被拒 token 数 L_rejected 要等验证完才知道，但调度只需要知道上限 Δ = L_draft + 1——只要 L_draft 事先已知（Eagle 等方法都满足），异步依然成立。

第二斧：输入准备的 GPU 化

每步都要准备三类输入：标准 LLM 输入（token、position、多模态 embedding）、注意力元数据（块表、序列长度）、每请求采样参数（temperature、top-p…）。挑战来自：

  • 规模：上千请求时，Python 逐条遍历记账，即便每请求 1 μs 也是 1 ms——吃掉 10 ms 预算的十分之一；
  • PyTorch 派发开销：大量小张量操作（索引、拼接、切片），一次简单 tensor[i] 都可能数十微秒；
  • 隐式 CPU-GPU 同步：某些操作会强制 CPU 阻塞等待 GPU，直接摧毁流水线。
① GPU 侧准备

用精心编写的 Triton kernel 在 GPU 上准备输入：上千请求并行处理，彻底绕开 Python 解释器与 PyTorch 派发 → 微秒级而非毫秒级

② 统一虚拟寻址 UVA

让 GPU kernel 直接访问已注册的 CPU 锁页内存，CUDA 运行时透明处理传输 → 消除显式拷贝

③ 增量状态更新

跨步保持持久化状态，只更新变化项。每步开销 ∝ 变化的请求数，而非总批次数

案例：块表管理。批大小 1000、最大序列 100 万 token、每块 16 token → 块表有 6250 万个条目、250 MB。vLLM 的做法：① GPU 上维持持久化块表缓冲区；② 调度器只把新增块 ID 的增量（delta）写进锁页内存，轻量 GPU kernel 通过 UVA 直接读取并应用；③ 前向时由 GPU kernel 完成按调度顺序的 gather。
结果：CPU 唯一的活儿就是写那一小撮增量，其余全在 GPU 上并行完成 —— 近乎零 CPU 开销。§4.6.2

第三斧：分段 CUDA Graph

PyTorch 的逐算子派发在小批次时可能吃掉大部分端到端延迟。CUDA Graph 能把一整串 GPU 操作录下来一次重放，绕开 eager 开销，但它有三条严苛约束：形状固定、图内不能有 CPU 操作、内存地址静态——而 LLM 推理的批大小、序列长度、注意力实现选择全是动态的。

图 9：Full vs Piecewise CUDA Graph（重绘自原文 Fig. 4.5 / 4.6）
关键观察：Transformer 中的"动态性"分布并不均匀——注意力是动态的（变长序列、动态调度、自适应 kernel 选择），而周围的线性投影与 FFN 是无状态的、逐 token 的，完全可以静态捕获。于是按执行特性切分：图捕获区域 + eager 注意力区域交替执行，用 torch.compile 的 graph break 标注自动生成边界。

第三讲小结

  • 抽象取胜：用 num_total_tokens / num_computed_tokens 两个标量 + Δ 规则，把 prefill/decode/抢占/分块/流式/前缀缓存/PD 分离/投机解码全部统一，从而实现优化的任意组合。
  • 调度演进：FIFO（简单但有队头阻塞）→ SRTF（TTFT 最优但会饥饿、开销大）→ 两级调度（waiting-FIFO + staging-SRTF，容量 8，兼顾有界开销与防饥饿）。
  • 三板斧：异步调度（提前一步，藏进 GPU 计算）、输入准备 GPU 化（Triton + UVA + 增量更新）、分段 CUDA Graph（静态部分捕获、注意力保持 eager）。
  • 接口与可移植性：极简用户接口（vllm serve）+ 三类开发者接口，模型编写只需遵守两条要求，自动融合与并行切分都尽量不侵入模型代码。

4第四讲 总结与未来方向对应 Ch.5

4.1 三大贡献回顾

① 算法：PagedAttention

把 KV Cache 的逻辑结构与物理布局解耦，切分为可非连续存放的固定块。近乎零碎片 + 块级共享，让 beam search、并行采样等复杂解码大幅省显存。

② 系统：vLLM 引擎

模块化架构分离接口/调度/执行；统一调度抽象；SRTF + 多级队列取得 SOTA 级 TTFT 且不饥饿；异步调度 + 分段 CUDA Graph 抹掉 CPU 开销。

③ 生态：开源影响

凭"通用、灵活、开放"三原则，支持稠密 Transformer、MoE、多模态；其架构模式被其他推理框架采纳，成为社区级基础设施。

4.2 三个未来方向

方向一：面向 Agent 工作流的有状态推理

Agent 会调用工具、循环迭代、依赖复杂，超出了传统的"请求–响应"范式。未来推理系统可能需要显式支持有状态推理，让 Agent 在长交互中保持持久上下文而无需反复重传历史。有希望的路径：

  • 跨副本 / 跨集群 KV 共享：一个引擎做的 prefill，通过共享存储或 KV Connector 被其他引擎复用；
  • 与外部/分层存储集成：把 KV 块透明地溢出到对象存储或专用 KV 存储，使上下文长度突破单节点显存；
  • 为分布式多租户环境设计缓存一致性模型、淘汰策略与安全约束。

方向二：训练与推理的统一

已有工作证明 vLLM 的模型编写接口可与训练框架（如 TorchTitan）打通并实现逐位一致。进一步统一将带来：

  • 简化"研究原型 → 生产系统"的路径，支持复杂的 on-policy 训练循环；
  • 支撑在线持续学习：推理请求直接成为实时训练信号，replay buffer 来自真实流量；
  • 逐位一致确保训练时算的对数概率与推理输出精确吻合，避免数值偏差污染梯度估计；结合 LoRA 等方法，指向"边服务边自我改进"的系统。

方向三：可靠性、可调试性与安全

  • 确定性 / 可重放的执行模式，便于调试；
  • 对 KV 使用、调度决策、单 token 延迟的细粒度追踪；
  • 与调度和执行协同的模型级安全机制接口（内容过滤、验证模型、工具使用约束）。
结语

vLLM 不是一个静态成品，而是一个地基。当模型走向万亿参数、上下文走向近乎无限、应用走向自主 Agent 时，本论文确立的三条原则——高效内存管理、灵活抽象、统一调度——仍将是关键。

A.3 思考题

Q1 · 为什么"加大批次"能提升吞吐，却又不能无限加大？
加大批次提高算术强度、摊薄权重读取开销；但受限于 ① KV Cache 显存容量 ② 单步延迟（TPOT）变差 ③ 激活峰值显存。token budget 就是用户在吞吐与延迟之间设定的旋钮。
Q2 · 分页为什么能同时消灭内部碎片和外部碎片？
按小块按需分配 → 浪费被限制在最后一块内（内部碎片可控）；所有块大小一致 → 任何空闲块都能被任何请求使用（不存在外部碎片）。
Q3 · 块大小取 16 是如何在两个相反力量之间取平衡的？
太小：kernel 无法充分利用 GPU 并行度、块表膨胀、共享粒度虽细但管理开销大；太大：内部碎片增加、共享概率下降（序列比块还短时尤其糟）。消融显示 16 在两类负载上都稳。
Q4 · 统一调度框架里，"抢占"为什么只是把 num_computed_tokens 置零？
抢占 = 丢弃该请求已算好的 KV Cache。恢复时，由于 prompt 与已生成 token 可以拼成一个新 prompt，一次 prefill 迭代就能重建全部 KV——不需要逐个 token 重放。
Q5 · 为什么 SRTF 会"天然优先 decode"，且能提升前缀缓存命中率？
decode 请求每步剩余量恒为 1，prefill 请求 > 1，SRTF 取最小者 → decode 自动靠前。缓存命中多的请求剩余量少 → 也会先被调度，赶在缓存块被淘汰前用上。
Q6 · 异步调度为什么可行？它损失了什么？
可行是因为调度决策不依赖模型输出：两个状态标量仅凭调度决策即可更新。损失在于输出 token 的 KV 缓存登记被延后一步，极端情况下会略微降低前缀缓存命中率——实践中罕见且收益远大于损失。
Q7 · Piecewise CUDA Graph 为什么偏偏把"注意力"留在 eager？
因为动态性集中在注意力：变长序列、动态调度决策、自适应 kernel 选择，都违反 CUDA Graph 的"形状固定/无 CPU 操作/地址静态"约束；而投影与 FFN 是无状态、逐 token 的，适合捕获。
Q8 · 什么情况下 vLLM 的内存优化会"失效"？
当瓶颈不再是显存而是算力时（如 175B 模型 + 短序列 Alpaca + 充裕 KV Cache 显存），Orca 也能塞进大批次，此时系统转为算力受限，内存管理优势被抹平。
