面向机器学习系统的智能体化 GPU 编程

机器学习系统的训练与推理都依赖快速的 GPU kernel。注意力机制、矩阵乘法以及各类融合算子在这些系统中占据了相当大的计算量。改进它们的实现，可以减少运行一个模型所需的时间与资源。

要让这些 kernel 变快，需要算法、GPU 硬件和编程模型三方面的深入知识。而代码智能体（coding agent）正越来越多地承担起这项工作：寻找相关实现、编写 kernel、解读诊断信息、并决定下一步尝试什么。要真正用好这些能力，需要一套能组织这些工作的工作流（workflow），以及一个能让智能体获取所需知识与反馈的环境（environment）。

本书介绍智能体化 GPU 编程的主要组成部分。你将了解一个由编译器驱动的支撑框架如何帮助智能体表达优化思路、诊断错误、测量性能，并保留值得留存的结果。这些能力共同构成一条高效的优化流程。

书中依次构建出：编译器基础层、领域特定的程序分析、知识库，以及 GPU 基准测试与性能剖析。随后展示智能体工作流如何与这套编译器支撑框架组合，引导一次完整的优化运行。

这些内容来自构建与使用智能体化 GPU 编程系统的真实经验。本书是 Modern GPU Programming for MLSys （《面向机器学习系统的现代 GPU 编程》）的 companion book（姊妹篇），我们计划将其纳入卡内基梅隆大学的 Machine Learning Systems（机器学习系统）课程系列。

第 1 章概述

机器学习系统在训练与推理上都依赖 GPU kernel，因此让这些 kernel 更快，可以减少运行一个模型所需的时间与资源。然而，要获得这些收益，需要一个迭代式的工程过程：探索各种实现方案、借助硬件知识与已有代码，并通过调试和测量不断打磨结果。随着代码智能体能力增强，它们已经可以承担其中越来越多的工作。

然而，智能体的大量精力可能消耗在优化工作之外的环节上：预判 kernel 代码将如何被 lowering（ lowering：降级映射）成硬件行为、排查依赖时序的偶发故障或被 GPU 并发活动干扰而失真的测量结果、寻找与当前任务相关的实现或优化策略。这会显著降低 token 效率：智能体把预算花在了消除这些不确定性上，留给探索优化方案的空间就更少了。于是不少本可行的优化，在实际的搜索预算内根本无法被触达。

这些问题并不能简单地靠"让智能体多试几个变体"来解决。它们指向的是开发环境中缺失的关键环节：可预测的编程基础、支持跨单次执行进行推理的工具、可复用的实现知识，以及可控的评估体系。这些环节合在一起，构成了面向智能体构建的、以编译器为基础的开发环境的需求——我们将用 compiler harness（编译器支撑框架） 这一术语来称呼它。

随着智能体编程把更多工作从"编写代码"转向"塑造智能体所处的运行环境"，我们预计这一层会变得越来越重要。这个思路受到当前若干面向 AI 的系统设计工作的启发。CAKE 明确提出了编译器与智能体的协同设计（compiler–agent co-design），其中包括一种支持验证与诊断的自演化程序表示。OpenAI 的 Jalapeño 则体现了相关的全栈设计原则：把编程目标本身设计得足够清晰、可预测，让 AI 能够有效开展优化。

在本章中，我们将描述智能体化 GPU 编程的各个组成部分，以及编译器支撑框架与智能体工作流是如何配合在一起的。

智能体化 GPU 编程的组成部分

智能体化 GPU 编程把以下要素结合在一起：编译器基础层、领域特定的编译器分析、知识库、基准测试与性能剖析，以及智能体工作流。前四者构成编译器支撑框架；而智能体工作流负责协调智能体在一次优化运行过程中如何使用它。

编译器基础层（Compiler Foundation）

智能体需要一种方式来表达和编译 kernel，并且在源代码与 GPU 操作之间有清晰的对应关系。编译器支撑框架可以构建在一个精简、稳定的中间表示（IR）之上，使操作、内存访问和同步都显式可见。保持 IR 规模小，可以让智能体需要推理的概念更少；而语义稳定则能在编译器更新迭代中保持程序含义不变。IR 还应当能对硬件原语扩展，以便随着硬件演进加入新的指令与同步机制。

领域特定的编译器分析（Domain-specific Compiler Analysis）

一次失败的测试可能只告诉智能体"这个 kernel 是错的"，却不说明是哪个操作导致了失败。有些错误可能只在特定输入或特定执行顺序下才出现。领域特定的编译器分析利用程序结构和 GPU 执行语义，对程序行为做出超越单次测试运行的推理。它给出的诊断信息应当解释清楚"哪里出了问题"，并定位到相关的程序操作。

知识库（Knowledge Base）

知道"分块（tiling）或流水化（pipelining）能提升性能"，并不等于智能体知道如何针对某个具体算子、某块具体 GPU 把它实现出来。知识库提供完整的 kernel 示例，展示算法、数据布局与调度（schedule）是如何配合在一起的。硬件与指令集文档则解释有哪些操作可用、以及它们的使用条件。这些来源合在一起，让智能体既能找到具体的策略，也能理解如何对它做适配。

基准测试与性能剖析（Benchmarking and Profiling）

一次耗时下降，可能反映了 kernel 确实变好了，也可能只是反映了其他 GPU 任务的干扰，或是前一次实验残留状态的影响。可靠的基准测试需要受控的执行条件，以及一致的正确性检查与计时测量规则，这样候选方案之间才具有可比性。性能剖析则对这些测量形成补充，展示时间花在哪里、硬件资源是如何被使用的。这能帮助智能体识别性能瓶颈，并决定该优化 kernel 的哪一部分。

智能体工作流（Agent Workflows）

一个优化任务通常要做很多次实验、很多轮智能体交互。智能体工作流负责协调这些工作：它决定任务如何分配、工作如何跨轮次延续、以及一次运行何时停止。在这套工作流之内，智能体使用编译器支撑框架来检索相关知识、实现 kernel，并获取正确性与性能反馈。

编译器支撑框架可以与不同的智能体工作流组合使用。每一种工作流都可以使用同一套知识、工具与评估接口。

把各部分连起来

工作流负责协调整个优化过程，编译器支撑框架则提供智能体在此过程中使用的各项能力。

在工作流中，智能体检索知识以形成策略，把策略表达为一个候选 kernel，并借助程序分析来排查缺陷。它还会在目标 GPU 上检查正确性并测量性能，同时用性能剖析来理解结果。这些交互为智能体提供了修复候选方案、定位瓶颈或改换思路所需的信息。而工作流则把任务在多次实验、多轮智能体交互之间向前推进。跨运行地看，经过验证的 kernel 可以反哺知识库，而优化过程中暴露出的问题则会指引分析工具与支撑框架的改进方向。

后续各章将依次展开这些要素：

  • 领域特定的编译器分析 展示一次分析如何对 kernel 做出超越单次执行的推理，并报告哪些操作应当为某个缺陷负责。
  • 面向智能体的知识库 描述可复用 kernel 与硬件文档是如何组织的，使智能体能够找到策略并针对手头的算子与 GPU 做适配。
  • 基准测试与性能剖析 涵盖让候选方案具备可比性的受控执行与测量规则，以及展示 kernel 时间开销分布的性能剖析。
  • 智能体工作流 解释智能体工作流如何与编译器支撑框架组合。

编译器基础层让 kernel 变得可分析，把经过整理的 kernel 维持在智能体可复用的形态，并对每个候选方案做即时编译（just-in-time）。第二部分将介绍这样一个基础层的具体实例，它提供本书后续各处使用的示例。

第 2 章领域特定的编译器分析

设想一个智能体在优化 GPU kernel 时遇到了一次偶发的挂起（hang）。超时本身几乎不提供任何线索：不知道是哪个操作被阻塞、也不知道为什么。于是反复重跑只会消耗掉智能体的调试预算，却无法帮它定位原因。智能体需要的是这样一类反馈：它能指向程序中相关的部分，并帮助智能体理解这次失败。

领域特定的编译器分析利用编译器对操作、布局（layout）与同步的表示，来检查一个 kernel 如何计算数值、如何访问内存、以及如何协调执行。这为智能体提供了可用于排查失败、评估正确性的反馈。

在本章中，我们将描述领域特定的编译器分析如何提供反馈，帮助智能体排查失败并检查正确性。

反馈需要满足的要求

一个优化任务会把"检索—实现—评估"这个循环重复成百上千次，因此面向智能体的正确性反馈必须满足三项要求：

  • 廉价（Cheap）：它要能在每一次迭代上运行，理想情况下不需要 GPU。
  • 可定位（Localizing）：它能指出不匹配的那个输出元素，或指出同步错误、数据竞争中所涉及的那些源操作。
  • 对范围表述明确（Explicit about scope）：一份报告必须说明它所覆盖的假设与程序行为。任何基于具体执行的检查，都只能对它实际测试过的那些输入得出结论。当一项检查无法完成时，它必须报告"结果不完整"，而不是把它当成通过（pass）。

静态分析从程序及其执行模型出发进行推理；CPU 仿真则通过跟踪具体输入来补充前者。两者都可以利用编译器对操作、布局与源码位置的表示，返回有用的诊断信息。 下面介绍的算法演示了这些能力的一种可能实现方式；一个编译器支撑框架完全可以通过其他分析算法提供同类反馈。

数值正确性验证

数值验证通常意味着把 kernel 放到 GPU 上跑一遍，再拿输出与一份独立编写的参考实现（reference）做比较。但 GPU 并不总是可用：它可能正忙于其他任务而需要排队。定位一个单独的错误，往往意味着插入打印语句、反复重跑很多次；如果每一次运行都要等 GPU，进展就会急剧变慢。

这里的思路是：让 CPU 代替 GPU 来执行这个 kernel。关键在于忠实性（faithfulness）：仿真必须执行代码实际所做的事情，而不是它本意要做的事情。如果把 kernel 翻译成等价的数组运算，那就等于已经假定了正确的下标与布局——而错误恰恰就藏在那里。一次忠实的仿真需要：

  • 遵循 GPU 执行模型：例如为每一个 lane 保留独立的值，并记录在每个分支上哪些 lane 是活跃的；
  • 尊重指令语义：包括舍入（rounding）、类型转换，以及 warp 内部的数据交换；
  • 从真实布局计算地址：把逻辑下标换算成物理字节，这样在仿真中，指向同一块存储的不同变量也会共享该存储。

这类仿真可以帮助智能体排查一部分内存错误与数值不匹配。在执行过程中，它可以报告越界访问（out-of-bounds）和对未初始化内存的读取。智能体还可以在不把 kernel 跑在 GPU 上的前提下，把仿真输出与独立参考实现做比较。这种比较会按输出名称和逻辑下标指出不匹配的元素，并给出它们的实际值与期望值。

然而，如果仿真以固定顺序执行各个 warp，就可能漏掉在其他执行顺序下才会出现的错误。要检查这类错误，就需要同时考察 warp 之间的协作关系以及它们内存访问的先后顺序。下面两节分别描述用于这两个目的的同步分析与竞争检测。

同步协议验证

共享数据的多个 warp 需要一套规则，规定每个参与者何时可以读取或覆盖这份数据。同步协议（synchronization protocol）就是协调它们工作的一组规则，通过"发送信号（signal）"与"等待（wait）"来实现。

举例来说：生产者写入一个 tile，并发出"已就绪"信号；消费者在读取该 tile 之前等待这个信号，读完后再发出"已完成"信号。而在用下一个 tile 覆盖缓冲区之前，生产者必须先等待消费者的完成信号。这些规则合在一起，就定义了在生产者与消费者之间安全传递数据的协议。

一个 kernel 可以用 mbarrier（一种 GPU 同步原语）来实现这些信号与等待。在上面这个协议里，每个 mbarrier 会记录称为 arrival（到达） 的信号，并在所需的 arrival 都已发生后允许一次 wait 完成。可以用一个 mbarrier 跟踪 tile 是否就绪，另一个跟踪缓冲区是否可用。这些信号与等待中的错误，会以几种方式破坏协议：

  • 到达计数不匹配（Arrival count mismatch）：实际的 arrival 数量与初始化时设定的计数不一致，导致某次 wait 永不返回。
  • 循环等待（Circular waiting）：两组 warp 各自都在等对方先完成，结果谁也无法继续。
  • 生产者超前（Producer overtaking）：生产者宣布每个新 tile 就绪，却不等待消费者用完上一个。于是消费者还在用这块缓冲时就可能被覆盖；而复用 barrier 阶段（phase）的协议，还会丢失"当前哪个 tile 是就绪的"这一信息。

这些错误可能只在某些执行顺序下才出现。由于 GPU 并不保证各个 warp 的相对推进速度，重跑同一个 kernel 可能改变这个顺序，从而让失败消失。因此数值测试无法稳定复现这类 bug，而人工审查在多级流水线中也极易漏掉这类交互。同步分析为智能体提供了一种手段：通过考察各种可能的执行顺序来发现协议错误。

一种可能的算法：状态搜索

要发现这类错误，必须考察 GPU 测试中观察不到的那些执行顺序。一种可能的算法会先抽取出一个同步模型，再搜索它的各种可能执行顺序：

  1. 只保留同步信息。 只记录：每个参与者当前处在什么位置、每个 barrier 处于哪个阶段（phase）以及还需要多少次 arrival、哪些异步操作尚未完成。这些合在一起构成一个状态（state）。
  2. 把操作转化为状态转移。 定义每个操作如何改变被建模的状态。一次 mbarrier arrival 会更新其到达计数，并可能完成一个阶段；而一次 wait 只有在它所期待的阶段完成之后，才让等待方向前推进。
  3. 搜索全部可达状态。 从初始状态出发，尝试每一个可以执行的事件：如果某个状态下程序尚未结束却没有任何事件可以继续推进，那就是死锁（deadlock）；如果发生了规则所禁止的状态转移，那就是协议错误。
  4. 返回反例（counterexample）。 把导致该错误的执行顺序交给智能体，并附上所涉及操作的源码位置。

真实 kernel 中的状态数量增长很快，因此搜索还必须合并重复状态，并剪枝那些仅在独立事件先后顺序上有差别的执行路径。

数据竞争检测

一个 kernel 完全可能完成了它的同步协议，却仍然存在两个 warp 在缺少必要顺序约束的情况下访问共享数据的情况。对同一块内存的两次访问，其中至少一次是写操作，且两者之间没有保证的先后顺序，就构成一次数据竞争（data race）。此时结果取决于谁先执行，于是有时正确、有时错误。常见形态包括：

  • 过早复用缓冲区：消费者发起一个读取共享内存的异步矩阵运算，随后立刻通知生产者可以写入；但该运算可能尚未读完，于是生产者的下一轮数据就把它覆盖了。
  • 别名（Aliasing）：两个名称不同的变量指向同一块存储，通过其中一个进行的写操作，与通过另一个进行的读或写之间没有顺序约束。
  • 保护错了访问对象：某个 barrier 确实发挥了作用，但它并没有保护那两个真正冲突的访问。

通过数值测试并不能排除数据竞争。在上面"过早复用缓冲区"的例子中，只要异步读在生产者覆盖缓冲区之前完成，结果就是正确的。负载或时序的变化可能改变这个顺序并暴露错误，使失败呈现间歇性、难以复现。因此，竞争检测必须检查程序是否为相互冲突的访问建立了顺序，即使在被测的那次执行产生了正确结果时也是如此。

一种可能的算法：向量时钟

检测竞争需要知道程序为哪些内存访问建立了顺序。当对同一内存位置的两次访问（其中至少一次为写）在任何一个方向上都不存在 happens-before（先行发生）关系时，就发生了数据竞争。这里，A happens before B 表示：根据程序的执行规则与内存序规则，A 排在 B 之前。

跟踪这一关系的一种可能算法使用向量时钟（vector clock）。分析把每个独立推进的参与者（例如一个 warp）视为一个执行者（executor）。它为每个执行者建模的事件（如内存访问与同步操作）按 1、2、3……依次编号。对每个执行者，分析维护一个向量时钟——即它本地视角下"每个执行者推进到了哪里"，其中每个执行者对应一个计数器。这些视角可以各不相同，因为一个执行者是通过同步才得知其他执行者的进展的，而不是仅仅因为对方跑得快就已经知道了。

举例来说，考虑 warp 3 与 warp 7 在完成共同初始化之后的情况。它们各自持有一个含 [W3,W7] 两项的时钟。warp 7 的时钟 [2,3] 记录了：它自己进行到第 3 个事件，且 warp 3 的前两个事件 happens-before 它。此时 warp 3 可能已经推进到第 5 个事件；但在同步把这一进展传递过来之前，warp 7 眼中 warp 3 仍停留在 2。

为了检测竞争，分析在每次内存访问时保存当时的时钟。当 A 的时钟中每一项都小于或等于 B 的时钟中对应项、且至少有一项严格更小时，A happens before B。如果两个时钟都没有以这种方式排在对方之前，那么这两次访问就是无序的（unordered）。当这样的无序访问触及同一位置、且至少有一次是写操作时，就构成数据竞争。

分析用两条规则来维护这些时钟：

  1. 本地推进。 在每个被建模的事件上，通过递增自身那一项来更新该执行者的时钟。同一时钟中对应其他执行者的项保持不变：另一个 warp 跑在前面这件事本身，并不能确立 happens-before 关系。
  2. 在同步处合并。 当同步确立了从一个执行者到另一个执行者的顺序时，把发送方的时钟合并进接收方的时钟——对每一对项取最大值，然后递增接收方自身那一项。取最大值保留了每个执行者已知的最新事件，包括发送方通过更早的同步所了解到的那些事件。

哪些操作能确立顺序、以及针对哪些执行者确立顺序，由目标硬件的内存模型决定。在新硬件上，算法可以保持不变，但这些规则必须重建，并用小测试在真实设备上加以验证。

第 3 章面向智能体的知识库

优化一个 GPU kernel 需要借助实现经验与目标硬件的知识。这些知识往往散落在各个代码仓库与硬件手册里，因此智能体在真正尝试某项优化之前，可能要花大量精力去找相关资料。

知识库把可复用的 kernel 与硬件文档组织起来，供智能体检索和学习。它一方面提供已经成熟的策略作为起点，另一方面帮助智能体发现可用于全新优化的硬件能力。

在本章中，我们将描述知识库的内容，以及智能体如何利用它找到并改造优化策略。

Kernel Zoo（内核库）

智能体可能知道向量化（vectorization）、分块（tiling）或软件流水化（software pipelining）能提升 GPU kernel 性能，却仍然需要一个具体示例来告诉它这些技术该怎么落地。kernel zoo 提供完整的程序，展示算法、数据布局与执行调度是如何配合在一起的。智能体可以检视这些实现，并把其中的策略改造到自己的 kernel 上。

参考 kernel 主要有两个来源：

  • 成熟实现的移植版本。 来自 FlashAttention、FlashInfer、DeepGEMM 等库的 kernel，为智能体提供了具体的算法、布局与同步模式，可作为移植的起点。算法、布局与调度上的多样性，会拓宽智能体可使用的策略空间。
  • 由智能体开发的 kernel。 优化运行中产生的有用成果可以成为参考 kernel，并附上关于其关键优化点与适用场景的简短说明，以便后来的智能体复用。在可移植 kernel 很少的新硬件上，智能体可以根据算子定义与硬件文档从零创建初始实现。一旦经过验证与基准测试，这些实现就成为该 zoo 中首批参考 kernel，供后续智能体改造与改进。

跨 kernel 的知识复用

kernel zoo 中未必包含当前正在优化的那个算子，因此智能体需要能识别出其他算子实现里有价值的机制。下面两个例子说明：一份参考资料可以在不同尺度上作出贡献——第一个提供的是一种代数分解思路，第二个则是一条 load 指令上的缓存策略。

作为算法层面的例子，Gated DeltaNet 与 Kimi Delta Attention 是线性注意力的两种变体。两者都会对循环状态做衰减（decay），并施加 delta-rule 校正。Gated DeltaNet 对每个 token、每个 head 使用一个衰减因子，而 Kimi Delta Attention 对每个 key channel 使用一个衰减因子。二者的 分块形式化表述 都产生 M X = R 这样的系统：系数不同，但都具有单位下三角结构。因此，能求解其中一个的算法，同样适用于另一个。

其中的 Gated DeltaNet prefill kernel 采用分层方式求解这个系统：借助 warp 级 MMA，把 8×8 的对角块逆逐步合并为 16×16、32×32、64×64 的块。这些合并步骤依赖的是三角结构，因此它们同样适用于 Kimi Delta Attention 中的那个系统。智能体可以复用这套分层求逆策略，同时针对目标 kernel 调整块大小与操作数类型。

一份参考资料也可以只贡献一条指令层面的选择，即便它的算子在数学上完全不同。 例如，DeepGEMM TF32 prenorm GEMM port 在它的 TMA load 上使用了不同的 L2 缓存策略：左矩阵操作数用 evict_first，右矩阵用 evict_last。这些 load 位置展示了如何给不同的数据赋予不同的 L2 保留优先级。智能体可以把这一机制改造到自己的复用模式上：如果一个 kernel 只读一次原始输入，却要与另一个 kernel 交换中间 tile，那么它就可以对原始输入使用 evict_first，并倾向于保留中间 tile。这样就能把更多 L2 容量留给另一个 kernel 很快会读到的数据。

在这些例子中，智能体可以从 Gated DeltaNet 学到"如何把一个矩阵求逆拆成更小的子问题"，从 DeepGEMM 学到"如何选择在 L2 中保留哪些数据"，然后把这两个思路都改造到自己的 kernel 上。因此，即使参考 kernel 计算的是完全不同的算子，一个 kernel zoo 依然能提供有用的优化思路。

硬件与 ISA 文档

kernel zoo 只收录了已经有人实现过的技术，而在新硬件上这类技术很少。硬件手册与 ISA 文档描述的是硬件本身提供了什么：它的指令、内存层次、缓存控制与同步原语，以及正确使用每一项所需的条件。当一次性能剖析暴露出某个瓶颈时，智能体可以在这些文档中检索能够解决该瓶颈的机制，并把它转化为一条优化策略。因此，知识库需要具备可检索的、与目标硬件版本相匹配的文档。

举个例子：假设一个智能体正在优化两个通过全局内存交换临时 tile 的并发 kernel。它希望减少 HBM 流量——一旦消费者用完某个 tile，其内容就不再需要，把它写回就是白白浪费带宽。从 DeepGEMM 借鉴来的驱逐提示（eviction hint）能影响保留优先级，但脏 tile 在被驱逐时仍然会被写回。

在 PTX ISA 中检索避免该写回的方法后，智能体可以找到 discard.global.L2，它允许把仍在 L2 中的 tile 直接丢弃而不写回，从而省掉这部分不必要的流量。手册同时规定：被丢弃的数据将变为不确定值。因此智能体必须确保消费者在丢弃每个 tile 之前已经读完它。文档既提供了机制，也提供了使用该机制的条件。

第 4 章基准测试与性能剖析

智能体需要可靠的性能测量，才能判断一次 kernel 改动是否真的带来了提升。同一块 GPU 上运行的其他任务会干扰这些测量，因此基准测试运行必须与竞争性负载隔离开。

智能体还需要理解一个 kernel 为什么慢。性能剖析（profiling）能帮助识别时间花在哪里、是什么限制了性能，从而为智能体选择下一步优化提供依据。

在本章中，我们将描述如何隔离 GPU 实验以获得可靠的基准测试结果，以及如何利用性能剖析来理解性能瓶颈。

基准测试服务器

当多个智能体共享一块 GPU 时，并发的实验会在正确性检查、计时和剖析上相互干扰。一个具有误导性的结果可能把整个搜索带向错误的方向，因此执行环境需要跨智能体协调 GPU 访问。

实验之间还会通过遗留状态相互影响。临时文件与进程内存可能残留，而一个失败的 kernel 可能让它的 CUDA context 变得不可用。智能体当然可以自己去协调设备访问、清理工作区、重启失败的进程，但这等于给每一次搜索都加上了执行管理方面的负担。

目标 GPU 也可能位于远端服务器或边缘设备上。即使目标设备本身可以承载智能体，在一台独立的工作站上做开发，也能把设备更多的算力与内存留给 kernel 执行，并有助于保持测量的一致性。一个远程执行服务在目标设备上运行智能体的实验，并把结果返回给本地供检视。

这些需求催生了这样一种基准测试服务器：它把远程执行与实验间隔离结合起来。它应当为每次实验提供：对其所分配 GPU 的独占访问、一个私有的工作区，以及一个全新的进程与 CUDA context。该服务负责清理，并把结果返回给智能体的开发环境。

基准测试结果能告诉智能体某个候选方案是否更快，但要选择下一步改动，还需要理解时间在 kernel 内部花在了哪里、是什么限制了推进。因此，同一个服务也应当支持在目标 GPU 上做性能剖析，并返回时间线（timeline）与硬件测量数据供智能体检视。

核内事件跟踪（In-Kernel Event Tracing）

高性能 kernel 通常会把工作划分成若干阶段，例如载入一个 tile、在其上做计算、再写回结果。不同的 warp 可以各自承担这些阶段并重叠执行。单一的 kernel 延迟并不能揭示是哪个阶段拖慢了其他阶段，因此要定位它们协作中的瓶颈，需要：

  • 在 kernel 内部记录每个阶段的起止时间，并按 CTA 与 warp 分别记录；
  • 按语义为阶段命名，例如"等待 TMA 数据""MMA 计算""写回"，使时间线能映射回源代码；
  • 尽可能少地干扰被测执行：记录必须廉价，且不能引入它自己的同步。

IKET（In-Kernel Event Tracing，核内事件跟踪） 通过在 kernel 内部记录带时间戳的标记与命名区间（named range），提供了这样的视图。智能体在它想检查的阶段前后放置区间边界，然后比较这些区间在不同 warp 与 CTA 上的持续时长与重叠情况，从而定位过长的等待或负载不均。

在这条时间线中，MMA warp 每次矩阵运算本身执行得很快，却要花很长时间等待下一个 tile。载入阶段就是瓶颈，因此智能体应当去调查它为什么这么慢。

硬件计数器剖析

时间线能显示某个阶段在等待，但要确定原因，往往还需要进一步调查：是内存带宽、发射的指令太少，还是寄存器溢出（register spill）。硬件剖析提供：

  • 硬件计数器，包括吞吐率、占用率（occupancy）、内存流量、缓存命中率以及 warp 停顿原因；
  • 与代码关联的指标，展示采样到的停顿与内存访问集中在哪些位置；
  • 可选的采集范围，使智能体能够只检视与它的假设相关的那个 kernel 与那次调用。

NVIDIA Nsight Compute（NCU）负责采集这些测量数据。它的 剖析指南 描述了各类指标组与采集方法。智能体用这些测量来检验由时间线得出的假设。再举一个例子：大量的 local memory 流量会引导智能体去检查相关代码中的寄存器溢出指标与 local memory 指令。

本章开头的插图展示了这些视图是如何配合在一起的：计时把候选方案与基线排出先后；时间线定位某次等待；硬件测量帮助调查其原因。每一种结果都为智能体提供了证据，支撑它设计一个更具针对性的下一次实验。

第 5 章智能体工作流

优化一个 GPU kernel 往往需要大量实验。在产出一个正确的候选方案之后，智能体可能仍需调查某个瓶颈、并尝试另一种实现。要让这个搜索持续推进，就需要决定下一步试什么、把结果带进后续轮次、以及选择何时停止。

智能体工作流负责在多次实验与多轮交互之间协调这些工作。它为搜索提供连续性，而智能体则使用编译器支撑框架来实现想法并获取反馈。

在本章中，我们将描述不同的智能体工作流如何组织一次 kernel 优化搜索，以及如何与编译器支撑框架组合。

智能体工作流示例

同一个编译器支撑框架可以支持不同的工作流。下面的示例展示了每一种工作流如何在多次实验与多轮智能体交互之间组织搜索。

固定流水线（Fixed Pipeline）

带有预定义阶段的工作流，会给搜索的每一部分赋予明确的角色。例如，一条固定流水线可以重复这样一个序列： 研究（research）→ 编写 kernel → 性能剖析 → 提出方向（propose direction）。

流水线可以把不同的阶段分配给不同的子智能体（subagent），每个子智能体承担一项聚焦的任务。结果从一个阶段传递到下一个阶段，而提出的方向会引导下一轮迭代。

目标模式（Goal Mode）

工作流也可以只给智能体一个目标，让它自行决定如何推进。例如， goal mode（目标模式） 会在多轮交互中保持一个目标处于激活状态，而由智能体自行选择下一步做什么。这里没有预定义的角色划分：同一个智能体负责研究、实现和评估，随着任务推进自行选择下一个动作。

对于 kernel 优化，这个目标可以规定一个期望的加速比，以及所要求的正确性检查。

Flame Chase（接力追问）

一个追逐目标的智能体，可能会反复忽略同样的问题。交替使用不同的智能体可以给搜索带来新的视角，尤其是当这些智能体使用不同模型、具有不同盲区时。 Flame Chase 采用的就是这种方式：让两个智能体在同一个任务上轮流工作。

每一轮都从当前任务与当前仓库状态开始，并在一个全新的会话中启动。保存在仓库中的代码、结果与笔记，在两个智能体之间传递工作成果。每个智能体基于前一个智能体留下的内容自行决定如何继续，整个运行由一个共享的预算来约束。

与编译器支撑框架组合

智能体通过调用支撑框架的工具、并解释其返回结果，把工作流与编译器支撑框架连接起来。例如，一次性能剖析请求，可能来自流水线中被分配到某个阶段的某个子智能体，也可能来自一个正在追逐目标的智能体。两者都可以调用同一个工具，并收到同一类报告。工作流决定的是由哪个智能体来调用该工具，以及之后工作如何继续。

这个共享接口让不同的工作流能够复用同一套支撑框架。改变智能体之间如何分工，可以完全不影响它们的工具调用。反过来，如果剖析工具通过同一个接口返回了信息更丰富的报告，那么每种工作流中的智能体都能利用这些额外的反馈。

启动智能体 会把这套组合在 TIRx Harness 上付诸实践，并展示如何在一个 kernel 优化任务中使用目标模式或 Flame Chase。

精简、可预测的编译器基础层

编译器基础层决定了：智能体能把它编写的代码与 GPU 实际执行的行为对应到什么程度。智能体可能知道它想要的执行策略，却不知道该写怎样的源程序才能产生该策略。编译器的各种变换（transformation）也会让调试变复杂，因为一次失败可能源自 kernel 本身，也可能源自对它的编译。

TIRx 是一门面向机器学习 kernel 的领域特定语言（DSL）与编译器，在本支撑框架中充当编译器基础层。我们通过 TIRx-lite 来编写 kernel——这是 TIRx 的一个底层 Python 接口，直接暴露硬件指令、内存地址、warp 角色与同步操作。让这个接口紧贴 NVIDIA 的 PTX 指令集，可以减少智能体需要额外学习的语义；而 PTX 文档则为这些被暴露出来的指令提供了含义与使用要求。

该基础层的中间表示（IR）保留了循环、条件分支与缓冲区，使编译与分析能够作用于同一个结构化程序。硬件指令接口也让新指令更容易通过小规模扩展被暴露出来。对一条指令的支持，既包括它的编译器 lowering（降级映射），也包括（在可用时）一个可供分析工具检查的模型。

编译器基础层让硬件策略变得可表达，但智能体还需要实现层面的知识。TIRx Harness 包含一个由 kernel 实现与硬件文档组成的知识库。它的 kernel zoo 收录了具体的 TIRx 实现，展示算法、布局与调度如何配合在一起，其中包括从成熟 GPU 库移植而来的版本：

借助 KCoral 做基准测试与性能剖析

正确性测试、计时与剖析都需要一个受控的执行环境。如果多个智能体在无协调的情况下共享一块 GPU，那么一次耗时变化反映的可能只是并发活动，而不是 kernel 本身的改进。TIRx Harness 使用 KCoral——一个远程 GPU 评估服务——来协调对目标设备的访问。

KCoral 为数值检查、基准测试与剖析采集提供执行环境，并一并提供结果与诊断产物（artifact）。对于每一个被优化的 kernel，会有一个评估程序（evaluation program）规定它的输入用例、参考输出与计时规则。KCoral 提供运行该程序所用的受管 GPU。这就把"一次测量意味着什么"与"执行测量的那套机制"分离开来。

在性能诊断方面，该支撑框架集成了核内事件跟踪（IKET）与 NVIDIA Nsight Compute（NCU）。IKET 提供跨 warp 与线程块的命名阶段时间线，暴露等待与重叠情况。NCU 提供吞吐率、占用率、内存流量、停顿等硬件测量数据。这些视图把性能问题定位到 kernel 的具体部分。

把开发与评估分离，还允许目标 GPU 位于一台并不承载编码智能体的服务器或边缘设备上。同一套支撑框架可以在工作站上提供编程与分析工具，同时用 KCoral 在目标硬件上完成测量。

第 7 章TIRx 编译器基础层

智能体可能想要挪动一次等待、改变一种内存布局，或者使用一条新的 GPU 指令。要尝试这些想法，它需要在 kernel 代码中直接表达这些改动。上一章介绍了支撑这项工作的编译器基础层。现在我们转向本书使用的 TIRx-lite——TIRx 的底层 Python 接口。

这个接口把布局、指令选择与同步的责任交还给智能体。支撑框架的其他组件则为这项工作提供支撑：知识库提供实现示例，程序分析帮助排查错误，而 GPU 测量显示某次改动是否真的提升了性能。

在本章中，我们将描述智能体如何在 kernel 代码中表达一项优化、如何为一条指令添加支持、以及如何检视生成的程序。每个能力都用小例子引出，最后用一个 GEMM kernel 把它们串起来。

在 TIRx-lite 中表达程序

要把一个优化想法变成 kernel，智能体需要同时控制操作以及操作之间的依赖关系。我们先从一个调度改动开始，然后跟踪一条指令——从它在源码中的调用，一直到生成的代码。

在源码中表达优化

要让一次 load 与计算重叠，就需要控制消费者在哪里等待它的数据。智能体可以把这个等待直接写进 kernel 代码。 TIRx 架构 在一个共享对象模型中表示表达式、控制流、缓冲区与后端操作。更高层的 tile 操作可以在该模型内部展开为更低层的语句与调用，因此当某个任务从中受益时，可以抬高程序层次，同时又不失去对下一层的访问能力。

TIRx-lite 的 编写接口 在源码层面暴露布局、指令与流水线的选择。txl.smem_pool() 以显式的 swizzle 分配共享内存 tile，而各种 view helper 负责计算地址与指令描述符。txl.ptx 提供面向数据操作的显式 PTX 调用，并配有 CUDA 级别的控制流。txl.specialize() 用于分配 warp 角色，而显式的同步原语则让智能体自行放置等待与完成信号。

这种控制方式把数据就绪与缓冲区生命周期的责任留给了智能体。由编译器管理的调度固然可以减轻这份负担，但也会限制智能体能直接表达哪些调度改动。

举例来说，在操作数 load 已经发出之后，智能体可以把那些独立的工作移到等待之前：

# Before
pipe.full.wait(stage, phase)
compute_independent_work()
consume_loaded_tile()

# After
compute_independent_work()
pipe.full.wait(stage, phase)
consume_loaded_tile()

为新增指令添加支持

一项优化可能需要某条尚未通过 txl.ptx 提供的硬件指令。TIRx 支持通过注册操作数类型（operand type）、副作用（effect）与 PTX 生成规则（emission）来扩展指令接口。随后，kernel 代码就可以通过 txl.ptx 调用这条已注册的指令；而要让分析也支持它，在适用的情况下还需要一份描述其行为的模型。

把扩展保持在局部，可以减少为支持一条新指令而必须改动的编译器代码量。但它的含义仍必须在代码生成与分析两侧保持一致：两边必须对同样的操作数与副作用作出相同解释。

为了看清一条已注册指令是如何被使用的，考虑 add.f32。开篇插图里的那个向量加法 kernel，在一对 load 与一次 store 之间调用了它：

import tirx_kernels.tirx_lite as txl


@txl.kernel(warps=4, grid=lambda p: (p["n"] + 127) // 128)
def vector_add(
    a: txl.gptr(txl.f32), b: txl.gptr(txl.f32),
    out: txl.gptr(txl.f32), n: txl.i32,
):
    i = txl.cta_id() * 128 + txl.thread_id()
    with txl.If(i < n), txl.Then():
        x = txl.local_scalar(txl.f32)
        y = txl.local_scalar(txl.f32)
        txl.ptx.ld.global_.f32(x, a.ptr_to([i]))
        txl.ptx.ld.global_.f32(y, b.ptr_to([i]))
        txl.ptx.add.f32(x, x, y)
        txl.ptx.st.global_.f32(out.ptr_to([i]), x)

这些指令调用接收显式的操作数，且目的操作数在前。txl.If 与 ptr_to 构造了外围的控制流与寻址。

检视生成的程序

要判断一项优化，智能体需要把它在源码上的编辑，与 GPU 将要执行的操作对应起来。这些显式的指令调用会 lowering（降级）成生成的 CUDA 中的内联 PTX。下游的 ptxas 编译器负责机器级别的优化。kernel 对象会暴露它的中间表示（IR）、生成的源码以及已编译模块：

vector_add.func        # the TIRx IR used for compilation and analysis
vector_add.source()    # the generated CUDA source
vector_add.compile()   # a runnable module

在生成的源码中，每一次指令调用都会变成一条内联 PTX 指令，例如 add.f32 %0, %1, %2;。

例如，一次布局转换会被直接写成 PTX 操作：shuffle（寄存器内数据交换），或者带同步的共享内存 load 与 store。源码清楚展示了哪些线程在交换值、它们使用了哪些地址，因此当智能体改动生产者或消费者的布局时，可以直接编辑这些操作。这种可见性也要求智能体具备更多硬件知识。在更高层的接口中，一次布局转换可能代表了很多这样的操作；那时就需要检视生成的代码，才能理解这一条源码操作背后的实际工作。

示例：一个 GEMM kernel

一个完整的 kernel 必须把指令选择、内存布局与同步组合进同一个程序。在下面这个 GEMM kernel 中，我们可以一起看到这些选择：它在一个 CTA（线程块）上计算 D = A Bᵀ 的一个 128×128 tile，输入输出均为 FP16。 所有线程把 A 和 B 拷入经过 swizzle 的共享内存；由一个线程把 Tensor Core 的 MMA 发射到 Tensor Memory，并在它们完成时发出 mbarrier 信号；随后每个 warp 读回结果的 32 行，转换为 FP16 并写回。

import tirx_kernels.tirx_lite as txl

M, N, K = 128, 128, 64
MMA = "tcgen05.mma.cta_group::1.kind::f16"
IDESC = 0x08200010          # f16 x f16 -> f32, M=128, N=128, A and B K-major
TMEM_LD = "tcgen05.ld.sync.aligned.32x32b.x32.b32"


@txl.kernel(warps=4, grid=1)
def gemm(A: txl.gptr[txl.f16, (M, K)], B: txl.gptr[txl.f16, (N, K)],
         D: txl.gptr[txl.f16, (M, N)]):
    warp, lane, tid = txl.warp_id(), txl.lane_id(), txl.thread_id()

    # Shared memory: TMEM address slot, one mbarrier, swizzled A and B tiles.
    smem = txl.smem_pool()
    tmem_slot = smem.alloc((1,), "uint32")
    bar = smem.alloc((1,), "uint64", align=8)
    As = smem.alloc((M, K), "float16", swizzle=txl.SW128B)
    Bs = smem.alloc((N, K), "float16", swizzle=txl.SW128B)

    with txl.If(warp == 0), txl.Then():
        txl.ptx.tcgen05.alloc.cta_group__1.sync.aligned.shared__cta.b32(
            tmem_slot.ptr_to([0]), txl.uint32(N))
    with txl.If(tid == 0), txl.Then():
        txl.ptx.mbarrier.init.shared.b64(bar.ptr_to([0]), txl.uint32(1))

    # Load: thread t copies row t of A and of B into shared memory, 16 bytes at a time.
    r = txl.alloc_local([4], "uint32")
    for j in range(K // 8):
        txl.ptx.ld.global_.v4.u32(r[0], r[1], r[2], r[3], A.ptr_to([tid, j * 8]))
        txl.ptx.st.shared.v4.u32(As.ptr_to(tid, j * 8), r[0], r[1], r[2], r[3])
        txl.ptx.ld.global_.v4.u32(r[0], r[1], r[2], r[3], B.ptr_to([tid, j * 8]))
        txl.ptx.st.shared.v4.u32(Bs.ptr_to(tid, j * 8), r[0], r[1], r[2], r[3])
    txl.ptx.fence.proxy.async_.shared__cta()
    txl.ptx.fence.mbarrier_init.release.cluster()
    txl.ptx.tcgen05.fence__before_thread_sync()
    txl.cuda.cta_sync()
    txl.ptx.tcgen05.fence__after_thread_sync()
    tmem = txl.local_scalar(txl.u32)
    txl.ptx.ld.shared.u32(tmem, tmem_slot.ptr_to([0]))

    # Compute: one thread issues the MMAs into Tensor Memory and signals the barrier.
    with txl.If(tid == 0), txl.Then():
        txl.idioms.mma_chain(MMA, tmem, a=As, b=Bs, idesc=IDESC,
                             pred=None, accumulate=False, guard="pred")
        txl.ptx["tcgen05.commit.cta_group::1.mbarrier::arrive::one.shared::cluster.b64"](
            bar.ptr_to([0]))
    txl.cuda.mbarrier_wait(bar.ptr_to([0]), 0)
    txl.ptx.tcgen05.fence__after_thread_sync()

    # Write back: warp w reads rows 32w..32w+31 from Tensor Memory, converts, stores.
    acc = txl.alloc_local([32], "float32")
    out = txl.alloc_local([16], "uint32")
    row = warp * 32 + lane
    for c in range(N // 32):
        txl.ptx[TMEM_LD](*[acc[i] for i in range(32)],
                         tmem + (txl.cast(warp * 32, "uint32") << 16) + c * 32)
        txl.ptx.tcgen05.wait__ld.sync.aligned()
        for i in range(16):
            txl.ptx["cvt.rn.f16x2.f32"](out[i], acc[2 * i + 1], acc[2 * i])
            txl.ptx.st.global_.u32(D.ptr_to([row, c * 32 + 2 * i]), out[i])

    txl.ptx.tcgen05.fence__before_thread_sync()
    txl.cuda.cta_sync()
    with txl.If(warp == 0), txl.Then():
        txl.ptx.tcgen05.relinquish_alloc_permit.cta_group__1.sync.aligned()
        txl.ptx.tcgen05.dealloc.cta_group__1.sync.aligned.b32(tmem, txl.uint32(N))

可以分三个阶段来读这个 kernel。载入阶段选择共享内存布局，并把操作数拷入其中。计算阶段发射矩阵乘累加操作，并安排一次完成信号。写回阶段等待该信号、读取累加器并写回结果。分配与释放包围着这些阶段，用于管理 Tensor Memory 的生命周期。

这些选择为智能体提供了改动 kernel 的具体位置：它可以改变布局、指令或调度，并检视由此产生的程序。分析可以帮助诊断候选方案中的错误，但要评估其性能，则需要在目标 GPU 上做测量。KCoral 基准测试服务器 将描述 KCoral 如何提供这个执行环境。

第 8 章KCoral 基准测试服务器

上一章展示了如何表达并检视一个 kernel。而判定一个候选方案是否正确、是否够快，还需要在目标 GPU 上做测量。当多个智能体共享一块设备时，这些测量需要协调访问，并在实验之间做出隔离。TIRx Harness 使用的 GPU 评估服务 KCoral，就为正确性测试、基准测试与剖析采集提供了这样一个共享环境。

KCoral 把开发环境与承载目标 GPU 的机器分离开来。它的服务器端管理工作进程与 GPU 访问；而评估代码定义输入用例、正确性检查与计时流程。同一个服务可以支持不同的 kernel 基准测试与诊断工具，而无需把它们的评估规则嵌进服务器里。

在本章中，我们将通过一个小型实验描述 KCoral 的执行接口，然后考察该服务如何协调 GPU 访问、隔离实验，并支撑基准测试与剖析工具。

一个精简而通用的执行接口

一次远程实验需要说明"执行什么"以及"带回哪些结果"。KCoral 把它表示为一个程序（program）：一段有序的指令序列，描述它的代码、输入、操作以及被选中的输出。一个 program 可以包含字面量参数，也可以包含对先前指令所产生值的引用。四个核心操作描述了这一执行模型：

Core operation Purpose
upload Supply code, tensors, bytes, compiled libraries, or files.
get_function Select a named function or object from a module or library.
run Call a function using supplied inputs or earlier results.
return Select values or filesystem artifacts to return.

Python 客户端提供 Program 用于描述一次实验，提供 Client 用于访问该服务，并为上传目录、返回文件等操作提供了辅助函数。同一个执行模型可以容纳基准测试结果、剖析报告与诊断产物。

下面的例子把这些操作组合成一个 program，用于检查并计时一个逐元素 GPU 加法。KCORAL_URL 是一个正在运行的 KCoral 服务的地址，该服务上装有 PyTorch 与 cupti-python（用于 GPU 计时）。

import os
from kcoral import Client, Program

source = """
import torch
from kcoral.builtins import benchmark

def evaluate(n):
    x = torch.arange(n, dtype=torch.float32, device="cuda")
    y = torch.empty_like(x)

    def candidate():
        torch.add(x, 1.0, out=y)

    candidate()
    torch.testing.assert_close(y, x + 1.0)
    return {"correct": True, "timing": benchmark(candidate)}
"""

program = Program()
module = program.upload(kind="module", source=source)
evaluate = program.get_function(module=module, name="evaluate")
report = program.run(fn=evaluate, args=[4096])
program.return_(key="report", value=report)

with Client(os.environ["KCORAL_URL"]) as client:
    result = client.execute(program)

if not result.completed:
    raise RuntimeError(result.error)
print(result.results["report"])

module、evaluate 与 report 都是对将在服务端创建的值的引用。Client.execute 提交该 program；被上传的函数定义了检查与测量逻辑，而 return_ 则选中那份报告，使其在 result.results 中可用。

自包含的实验

重复一次实验，不应该要求重建先前运行留下的隐藏状态。因此，每个 program 都要明确声明它所需要的代码与输入——这些声明是相对于服务端已安装的编译器、库与 GPU 工具而言的。它不依赖前一次执行留下的张量、函数或临时文件。这个无状态接口让依赖关系变得显式，也允许在实验之间替换工作进程。

一次实验的输出可以成为另一次实验的显式输入。KCoral 会缓存已上传的内容以减少重复传输，但这个缓存并不会跨 program 保留活动的 Python 对象或 GPU 张量。每个 program 仍需声明它所需要的输入。

协调式的 GPU 访问

比较两个候选方案时，测量结果不能因为另一个工作进程同时使用同一块 GPU 而失真。KCoral 在专供该服务的 GPU 上协调各个实验。一次 GPU 租约（lease）授予某个工作进程对一块受管设备的独占访问权，用于检查、计时或剖析。共享同一块设备的多个工作进程轮流使用，而不同的设备则可以并行支撑实验。明确只使用 CPU 的函数可以在不持有租约的情况下运行。

租约协调的前提是：实验在释放设备之前已经完成了它们的 GPU 工作。它能防止协作中的工作进程之间出现重叠的 GPU 工作；而评估代码仍然决定测量流程本身，包括预热（warmup）、重复次数与输入选择。

隔离的文件与进程状态

一次实验留下的文件，可能影响另一次实验的代码或结果。启用文件系统隔离后，KCoral 使用 bubblewrap 为工作进程提供一个私有的可写工作区，以及只读的运行时依赖。其他工作进程的工作区是不可见的。每次执行都有一个临时工作目录，在完成（包括已被处理的失败）后被删除；需要保留的输出则作为显式的返回产物。

进程内存需要另一条边界。已导入的模块、各种分配以及一个 CUDA context 都可能在一个长生命周期的工作进程中持续存在，而一个失败的 kernel 可能让它的 context 变得不可用。默认情况下，KCoral 会在每个 program 之后替换工作进程，从而为下一次实验提供一个全新的 Python 进程与 CUDA context。工作区隔离与进程替换分别独立地处理这两类状态来源。

面向多个 GPU 主机的单一接入点

随着评估扩展到多台 GPU 主机，客户端需要一种提交实验的方式，而不必自行选择主机。KCoral 可选的 router（路由器）为多台各运行一个 KCoral 服务器的 GPU 主机提供统一的服务地址。router 负责准入控制并选择可用节点；每台服务器自行管理它的工作进程与 GPU 租约。开发工具使用同一个执行接口，无需跟踪各自主机的地址与可用状态。

集成基准测试、剖析与诊断

要理解一个 kernel 的行为、并识别出进一步的优化机会，智能体需要的不仅仅是一个耗时数字，还需要各类 GPU 工具的输出。这些工具各有自己的启动选项与输出格式。TIRx Harness 通过命令行适配器（adapter）把它们接入 KCoral。每个适配器打包所需的代码与输入，在服务端已安装的环境中配置该工具，并在本地暴露其输出与退出状态。对于会产生文件的工具，适配器还会取回被选中的产物：

Adapter Responsibility
kcoral_python.py Run a user-supplied Python script, command, or module for custom tests and experiments; return standard output, standard error, and exit status.
kcoral_iket.py Capture In-Kernel Event Tracing (IKET) timelines and save traces and retained intermediates locally.
kcoral_ncu.py Capture a Nsight Compute (NCU) hardware report for local inspection.
kcoral_compute_sanitizer.py Run Compute Sanitizer and retrieve selected diagnostic files.
kcoral_remote.py Evaluate a baseline or candidate using a packaged workload’s predefined correctness checks and timing procedure; return benchmark results.

适配器负责完成集成，而 KCoral 提供 GPU 协调与实验隔离。实验本身仍需提供 kernel、输入设置，以及任何所需的插桩（instrumentation），例如 IKET 的命名阶段标记。时间线、硬件报告与 sanitizer 的发现都属于诊断证据；普通基准测试才是确立性能比较的依据，因为剖析与插桩本身可能影响执行开销。

编译器基础层与 KCoral 一起，把源码改动与 GPU 结果连接起来：智能体可以表达一个候选方案、提交一次实验，并检视返回的测量数据与产物。第三部分将以一个 启动智能体 开篇，它使用的正是这些能力，随后再更细致地考察分析与基准测试反馈。

第 10 章编译器分析深入

上一章通过 Grouped GEMM、以 DeepGEMM 为基线，引入了智能体工作流。从这里开始，我们切换到一段录制好的 Kimi Delta Attention（KDA） 运行记录：它更复杂的 kernel 让我们能更深入地探索支撑框架的分析工具。本章跟踪智能体如何使用 Synccheck 与 Racecheck 来诊断并修复同步错误与数据竞争。

一次挂起或一次竞争，可能在很多次 GPU 运行中都潜伏不现，因此智能体需要不依赖时序的反馈。Synccheck 与 Racecheck 提供的正是这种反馈：它们在 CPU 上、以具体输入分析一个 kernel，并对照源码行号报告同步问题与数据竞争。这两个工具都构建在 NumSim 之上——这是一个 CPU 仿真基础层，用于建模 kernel 的操作与内存行为。

调用各项分析

为了能像编辑代码那样频繁地检查自己的 kernel，智能体直接在它的脚本中调用这些检查器。两个检查器都是 tirx_harness 中的 Python 函数，接收一个 TIRx PrimFunc 以及其实参的具体取值。TIRx-lite kernel 通过 kernel.func 暴露这一表示。Synccheck 示意图中的那个"生产者超前"kernel 只有一个参数——一个含 ROUNDS 个整数的输出数组——它这样调用 Synccheck：

from tirx_harness import racecheck, synccheck

report = synccheck(kernel.func, inputs={"out": np.zeros(ROUNDS, np.int32)})
report.print()           # findings with source excerpts
report.verdict           # "clean", "review", "incomplete", or "error"
report.to_dict()         # structured evidence
report.require_clean()   # raise unless the verdict is "clean"

在 Kimi Delta Attention 运行中，智能体遇到了全部四种判定：

第 12 章复盘与支撑框架改进

在采纳一个由智能体产出的 kernel 之前，我们需要理解它是如何取得加速的，以及它可以用在哪些地方。人工复盘（review）会对照原始任务，评估该 kernel 在数值上的改动、它对输入的假设，以及它的性能声明——把实现连同它的检查与测量一起审视。

人工复盘还会识别出应当被纳入支撑框架、供后续智能体运行使用的发现。在本章中，我们将描述如何复盘一次加速背后的各项假设，以及如何把复盘所得固化进支撑框架。

复盘加速背后的假设

首先，请智能体指出带来这次加速的那些改动，并说明它们在什么条件下仍能保持任务所要求的行为。对于数值层面的重写，这些条件可能涉及中间精度与取值范围；对于特化（specialization），这些条件可能会限制所支持的输入。

然后把这些条件与现有的验证做比较。凡证据不完整之处，让智能体用分析或测试去调查那条具体假设，并在需要时修订实现；由复盘者来判断所得证据是否足以支持采纳。

举例来说，早先一个由智能体演化出来的 Kimi Delta Attention kernel 通过了它的测试，但它对衰减（decay）计算的重写，可能让中间值发生下溢（underflow）或上溢（overflow）。

这次重写：把衰减因子分开计算

为了减少指数运算的次数，该 kernel 把前一个 token $j$ 与后一个 token $i$ 之间的衰减拆成了两个分别计算的因子。对某一个 key channel，令 $c_t$ 为从该 chunk 起点到 token $t$ 的累积以 2 为底的对数衰减。这次重写是

$$ 2^{c_i-c_j} \quad\longrightarrow\quad 2^{c_i}\left(\frac{1}{2^{c_j}}\right). $$

例如，从 token 1 和 token 2 到 token 3 的衰减，分别需要 $2^{c_3-c_1}$ 与 $2^{c_3-c_2}$。重写之后，两者使用同一个值 $2^{c_3}$。该 kernel 只计算它一次，再与已保存的倒数 $1/2^{c_1}$ 和 $1/2^{c_2}$ 组合。在一个 chunk 内，每个 token 的两个因子会被很多对（pair）复用。

这两个表达式在实数算术下是相等的，但当 kernel 用它的 fp32 指令分别计算这两个因子时就不相等了——因为极小的指数会被冲洗（flush）为零。

一个 0.5 的衰减如何变成 NaN

这个失败会在强衰减下发生，因为强衰减会让累积对数值变得非常负。考虑一个 64-token 的 chunk，其前 32 个衰减系数为 $1/16$。 每一个都给累积对数衰减加上 $-4$，于是在 token 32 处有 $c_j=-128$。 如果下一个系数是 $1/2$，那么在 token 33 处 $c_i=-129$。这两个相邻 token 之间的衰减本应为 $2^{-129-(-128)}=0.5$。

一旦累积对数衰减落到大约 $-126$ 以下，这种分开计算的方式就无法恢复出那个 $0.5$：

Calculation Result in this example
Earlier token: $2^{c_j}$ Flushed to $0$
Reciprocal: $1 / 2^{c_j}$ $+\infty$
Later token: $2^{c_i}$ Flushed to $0$
Combined decay $0 \times \infty = \mathrm{NaN}$

这些 NaN 会进入矩阵乘积，并可能经由循环状态传播下去；用 PyTorch 复现该 kernel 的这套算术，在强衰减下会在输出与状态中都产生 NaN。

这个候选方案之所以能通过，是因为早期的测试只达到约 $-54$ 的累积对数衰减，从未越过 $-126$ 附近的失败边界。收紧它们的误差容限，并不能在它们没有测试过的输入上暴露失败。

因此，基准测试有可能在奖励一个无效的优化。即便不存在故意作弊，这也是一种 reward-hacking（奖励劫持）风险。

修复并验证该候选方案

一旦有针对性的测试确认了这次失败，智能体就需要修订衰减计算，以避免那个在强衰减下会变成无穷的中间倒数。在取指数之前先计算对数衰减之差，是其中一种做法。为了保留矩阵乘的运算结构，智能体可以参考参考实现——后者从更小的块之间的边界起算衰减，并使两个因子都不超过 1。

随后，智能体应当在失败边界附近、以及在真实应用输入上测试修复后的 GPU kernel。每个 token 的输出与最终状态都必须在任务误差限内与独立参考实现吻合，并且要拒绝 NaN 与无穷值。由于修复可能改变性能，还要对照性能基线对修复后的 kernel 重新做基准测试。

改进支撑框架

如果一些发现只停留在某一次运行的文件与笔记里，后来的智能体很容易错过它们，于是会把同样的工作重复一遍。应当把它们固化进支撑框架，让后来的智能体通过它们已经在用的工具与之相遇。

扩大输入覆盖

把那些能在受支持域内暴露无效优化的输入，加入该任务的常规正确性检查。在这个例子中，强衰减用例会让这个不安全的因式分解在搜索过程中就失败。任务定义中已经包含了这一覆盖。

修复分析工具

当调试暴露出某个分析工具的缺陷时，用 trace 隔离出一个可复现用例（reproducer），并验证一项修复。例如，重放 Gated DeltaNet 的演化 kernel 时暴露了一个模拟器唤醒 bug，它让 Synccheck 误报死锁。把这个 reproducer 保留为回归测试，并把经过复盘的修复合入支撑框架。

复用经过复盘的 kernel

把经过复盘的实现加入 kernel zoo，并附上它所支持的输入、验证结果、计时数据，以及对关键设计选择的说明。一个经过复盘的 kernel 可以作为后续同类算子运行的起点，而它的设计笔记能帮助智能体把其中的技术迁移到相关 kernel 上。当 kernel 或编译器的改动可能影响结果时，要重新检查正确性与性能。

这些改动闭合了整个回路：下一次搜索将使用更好的检查、修好的工具，以及经过复盘的实现。

第 13 章进阶技巧

一次长时间的优化运行，即使在每一个工具都正常工作的情况下也可能陷入停滞。某次改动可能让 8,192-token 的输入变快，却让更短的输入变慢，于是留下一个掩盖了这种取舍的平均分数。一个起初更快的融合 kernel，可能导致智能体在探索某个拆分式实现的潜力之前就放弃它。而关于融合 kernel 的大量尝试笔记，又会让智能体持续聚焦于小规模的调度改动，而不是重新审视那个选择。

在本章中，我们将描述让一次长时间搜索保持高产的若干实践：先针对一个输入 shape（输入张量的维度，例如序列长度与 head 数）做优化，再推广；保留有潜力的备选方案；以及清理临时产物。

先优化一个 Shape，再推广

当应用需要若干种 shape 时，先从一个有代表性的 shape 开始。这能带来更快的性能收益，原因有两点：

  • 正确性检查与基准测试在单一 shape 上跑得更快，于是智能体花在等待工具上的时间更少，可以把更多时间用于推理和实现优化。
  • 单一 shape 给智能体一个更清晰的奖励信号。在多种 shape 下，同一次改动可能让一种配置变快、另一种变慢，从而更难判断该朝哪个方向走。

一旦智能体有了一个可用的候选方案，就把它扩展到其他所需的 shape 上。重新审视那些与初始 shape 绑定的假设，并对照扩展后任务的计算与验收标准，同时检查原有用例与新增用例。本部分中的 Kimi Delta Attention 任务固定了 H=96 与 T=8192。要推广它，请准备一个显式包含额外 shape 的任务，并以保留下来的实现作为那次搜索的起点。

保留有潜力的备选方案

即便只针对一个 shape，早期的计时结果也可能偏爱一种后来失去了改进空间的做法。请把当前最好的通过候选方案，与若干采用了不同优化思路的方案一起保留下来。例如，融合 kernel 可以减少启动开销与中间存储，而拆分各个阶段则能暴露更多并行工作、改善 SM 利用率。一个当前较慢的做法，可能为另一个 shape 或另一项优化提供了有用的起点。

请把每个候选方案的源码、检查、配套的计时数据，以及一段关于其独特点的简短说明放在一起。示例任务把这个池子称为 frontier（前沿）。请删掉冗余的版本，同时保留那些仍然提供了值得探索方向的备选方案。

清理临时产物

保留有用的备选方案，并不需要保留每一次尝试。过长的尝试历史会促使智能体不断打磨当前的路线，而不去重新审视它的各项假设。

请定期清理实验产物，例如每 12 小时一次。保留当前的 frontier；把更早的 scratch 候选方案、尝试历史与修改日志归档到智能体工作目录之外，这样它们仍然可供复盘使用。

在搜索过程中，当继续推进需要对任务做出改动或需要额外资源时，请及时介入。
